# Gemini 产出质量诊断与能力提升机制

> 版本：0.1
> 适用范围：Codex 复核 Gemini 产物、Mike 判断是否需要补权限/补上下文/返工时使用。

## 1. 为什么需要这个机制

Gemini 的产物出现问题时，不能简单归因为“不认真”或“能力差”。在多 Agent 协作里，低质量产物往往来自多个来源：

- 任务权限不足，导致它只能猜。
- 上下文没有同步，导致它基于旧事实工作。
- 任务验收标准不清，导致它以“写完文件”当作完成。
- 当前知识不够新，尤其外部平台规则、SEO 规则、竞品信息。
- 推理方式有问题，把“待核验”写成“已实现”。
- 输出格式没有被约束，导致 Mike 或 Codex 无法直接执行。

诊断目标不是追责，而是把每次返工转化为团队能力提升。

## 2. 问题归因分类

### A. 权限不足导致的质量问题

表现：

- 产物大量使用“可能”“应该”“推测”。
- 内容宣传了某个产品能力，但没有代码或后台事实依据。
- 对页面、模板、埋点、Webhook 等能力理解不准确。
- 明显需要看某个代码文件，但任务没有授权。

处理：

- 不直接判定 Gemini 质量差。
- 在返工任务中补 `CODE_READ_SCOPED`，只列具体文件。
- 要求 Gemini 在报告中写出“事实来自哪个文件”。
- 如果还缺文件，Gemini 必须使用 `[REQUEST_READ: /absolute/path]`，不能私自泛读 `Code/**`。

示例：

```text
问题：Webhook 博客对 HMAC 能力表述不清。
归因：部分属于权限/上下文问题。
处理：授权只读 Code/services/skills/webhook.ts，并要求区分 generic webhook、Feishu、DingTalk 的签名实现。
```

### B. 上下文不同步导致的质量问题

表现：

- 把已完成的功能列成待实现。
- 使用旧目标、旧价格、旧页面路径、旧博客状态。
- 忽略 Codex 最新复核意见或 Mike 最新决策。
- Top queue 中出现重复任务。

处理：

- 不直接开新任务，先让 Gemini 读取最新 sprint、team-board、review report。
- 要求它给出“已实现 / 未实现 / 需验证 / 延后”的分类。
- 对重复任务打回，要求去重。

示例：

```text
问题：Gemini 把 sitemap 包含 solution 页面列为待实现。
归因：上下文不同步或代码核验不足。
处理：让它读取 Code/app/sitemap.ts，并把该项改为生产验证任务。
```

### C. 知识过期或外部规则未知

表现：

- 对 BetaList、Indie Hackers、AlternativeTo、Reddit 等外部平台规则写得很确定。
- 对 Google SEO 规则、结构化数据、富摘要收益使用绝对话术。
- 对竞品定价、平台政策、目录审核周期做未经验证的判断。

处理：

- 如果 Gemini 没有联网能力，必须标记 `UNVERIFIED_CURRENT_RULES`。
- 不能把未核验外部规则包装成“可直接执行”。
- 需要 Mike 或 Codex 用浏览器/网页验证时，列成人工核验清单。

示例：

```text
问题：外部推广包宣称 Indie Hackers 可沉淀 dofollow 优质外链。
归因：外部规则未核验。
处理：改成“待核验假设”，输出平台规则核验表。
```

### D. 推理或判断错误

表现：

- 把“可验证”写成“已实现”。
- 把“可能提升 CTR”写成“大幅提升 CTR”。
- 把不稳定的 SEO 观察数据解释成确定趋势。
- 没有区分草稿、可发布、可上线、需部署。

处理：

- 返工时要求增加 `claim_type` 或 `factStatus`：
  - `confirmed`
  - `likely`
  - `needs_verification`
  - `do_not_claim`
- 对外发布材料必须只使用 `confirmed` 和保守的 `likely`。
- 对 SEO 效果类表述使用保守措辞。

### E. 任务颗粒度或验收标准错误

表现：

- 几分钟完成“6-8 小时任务”。
- 文件数量很多，但没有可执行 payload。
- 报告写“完成”，但 Mike 仍然不知道下一步怎么发布、提交、检查。

处理：

- 把任务从“写报告”改为“交付物清单”。
- 每个任务必须输出后台字段、JSON、核验表、执行步骤或可部署实现说明。
- 验收口径改成：
  - 能否发布？
  - 能否上线？
  - 能否请求索引？
  - 能否给 Codex 直接实现？
  - 能否让 Mike 执行外部动作？

### F. 输出格式不适合协作

表现：

- 文章只有 Markdown，没有后台字段。
- 外部推广只有文案，没有账号要求、截图要求、风险提醒。
- 实现清单只有想法，没有路径、风险、验证方式。

处理：

- 模板化输出。
- 博客必须包含 admin payload。
- 外部推广必须包含 rules checklist。
- 工程建议必须包含文件路径、状态分类、测试建议。

## 3. Codex 复核时必须做的归因判断

每次 Codex 复核 Gemini 产物时，至少回答：

1. 这个问题是权限不足、上下文不同步、知识过期、判断错误，还是任务验收不清？
2. 如果是权限问题，应该补哪个最小只读权限？
3. 如果是上下文问题，应该把哪些文件加入必读？
4. 如果是外部知识问题，是否需要联网/人工核验？
5. 如果是判断错误，应该加入什么事实状态字段？
6. 如果是任务设计问题，下一版任务要怎么改验收标准？

## 4. Gemini 执行报告新增要求

Gemini 在报告中必须增加：

```text
## 事实来源与不确定性

- 已确认事实：
- 基于代码确认的事实：
- 基于文档确认的事实：
- 需要 Mike 或 Codex 核验的事实：
- 不应对外宣传的内容：
```

如果任务涉及外部平台或近期规则，必须增加：

```text
## 外部规则核验状态

- 是否已联网核验：是 / 否
- 若未核验，标记：UNVERIFIED_CURRENT_RULES
- 需要 Mike 手动确认的项目：
```

Codex 复核报告必须增加：


## 6. 对 Gemini 的标准反馈方式

不要只说：

```text
你的报告质量不行，请返工。
```

应该说：

```text
本次产物需要返工，但问题不是单一质量问题。

归因如下：
1. 上下文不同步：你把已实现的 sitemap/use-case 遍历列成待实现。
2. 外部规则未核验：你把 BetaList/Indie Hackers/AlternativeTo 的执行条件写成确定事实。
3. 判断过强：你把“可能提升 CTR”写成“大幅提升 CTR”。

本次返工会补充以下上下文：
- Code/app/sitemap.ts
- Code/components/templates/template-use-button.tsx

你需要输出：
- 已实现/未实现/需验证/延后分类。
- 外部规则核验表。
- 更保守的 SEO 效果表述。
```

## 7. 长期能力提升路径

### 第一阶段：减少盲猜

- 更多使用 `CODE_READ_SCOPED`。
- 每次任务只给必要文件，不泛读。
- 要求事实引用到文件。

### 第二阶段：减少上下文漂移

- 每个任务强制读取最新 team-board、最新 Codex review、最新 sprint。
- 建立“已实现能力清单”，避免重复建议。

### 第三阶段：提高可执行性

- 内容产物转成后台 payload。
- 外部推广转成 rules checklist。
- 工程建议转成状态分类和测试计划。

### 第四阶段：形成专业化 Agent

未来可把 Gemini 的角色拆成：

- Content Research Agent：只做选题、草稿、内容事实核查。
- SEO QA Agent：只做索引、结构化数据、GSC 数据解释。
- Growth Ops Agent：只做外部目录、社区、UTM、执行清单。
- Engineering Audit Agent：只做只读代码审计和实现建议。

拆分前，Gemini 仍作为综合执行者，但任务必须更结构化。
