## 1. 执行摘要 (Executive Summary)

基于对 6 个核心关键词在 Google US SERP 的深度检索和对代表竞品页面承接路径的拆解，我们对 **Service Request / Customer Complaint** 主题得出如下核心结论：
*   **重系统意图与轻量表单的分界十分明确**：
    *   **重系统意图**：`work request form` 极度偏向**设施与设备维护管理系统（CMMS/Facility Helpdesk）**。用户通常寻找的是像 FMX、UpKeep 等带有工单状态机（Open/In Progress/Closed）、设备关联、SLA 时效响应的专业维护管理后台。
    *   **轻量表单意图**：`service request form` 和 `customer complaint form` 的搜索意图是通用的**客户咨询/反馈收集表**。用户主要期望收集客户的基础诉求或投诉描述。
*   **物理红线冲突**：GenForms 当前 MVP 版本**不支持任何后台工单状态流（Open/Closed）**，**不支持自动分派代理商（Agent Routing）**，并且**不支持文件上传（如设备损坏照片上传）**。
*   **最终决策**：**Merge into existing Topic `contact-us` with Template-only coverage (合并入现有的 `contact-us` 专题，仅做模板库覆盖)**。我们不需要为该场景开辟独立的营销落地页，以防吸引来需要高并发 ticketing 系统或内部维保流程的企业级用户，造成虚假承诺与极高客诉。

## 4. 深度意图与核心任务解构 (Deep Intent & User Tasks)

1.  **Search Intent (搜索意图)**：
    *   用户（主要是客服主管、IT 支持、设施主管或独立服务提供商）希望找到一个表单来接收客户的故障反馈、服务申请、维保请求或投诉。
    *   **核心期望**：提供清晰简洁的描述框、故障分类（Category）以及联系方式，并自动转发给处理人员。
2.  **User's Immediate Task (用户的即时任务)**：
    *   将表单内嵌在网站或发送给客户，当收到新请求时，能够实时将请求推送到内部群聊，或自动写入工单看板。
3.  **Expected Capabilities (期望的产品能力)**：
    *   客户基础字段（姓名、订单号、服务类型）。
    *   **文件/照片上传 (File Upload)**：非常核心，尤其在投诉（如“快递受损”）或维保（如“水管破裂”）场景中，用户极度需要上传证据照片。
    *   **SLA 追踪与工单分派 (Ticketing/SLA)**：在大中型客服场景，需要直接对接 Zendesk/Jira，或能对表单内容执行“状态流流转（处理中/已关闭）”。
4.  **GenForms Support Status (GenForms 支持状态)**：
    *   **不支持（红线排除）**：不支持文件上传，不支持控制台工单状态流（如“处理中”状态转换），不支持 SLA 逾期提醒，不支持向具体客服专员的 native CRM 指派。
    *   **支持**：一句话生成意见收集表；通过 Webhook 和飞书/Slack 机器人实时推送投诉摘要至团队支持群聊。

## 5. 代表竞品承接路径剖析 (Competitors)

*   **Zendesk (全套服务流)**：
    *   *承接路径*：提供 `/hc/en-us/articles/` 指导文档，让商户配置 Zendesk Web Widget 表单，提交后直接在后台生成带编号的 Ticket。
*   **Cognito Forms / Smartsheet (逻辑与协作流)**：
    *   *承接路径*：不仅有输入表，还能将数据同步入类似网格（Grid）的工作区，便于团队分工。
*   **启示**：由于 GenForms 没有 Ticket 状态机，如果直接以“Helpdesk/工单系统”做营销，将面临极高流失。我们应主打 **“轻量客服信息接收器”**，只做入口数据收集，通过 Webhook 把信息导向 Slack 或外部表格。

## 6. GenForms 契合度与边界分析 (GenForms Fit & Product Boundary Assessment)

### 6.1 绿线承诺：
*   **AI 生成个性化意见反馈表**：快速定制各种垂直品类的客户投诉与支持登记表。
*   **实时聊天机器人通知集成**：支持通过 Webhook 将服务请求转化为群消息格式，实时推送到客服人员的 Slack/飞书群中（群通知即是简单工单分配）。
*   **多端完美适配**：适合客户用手机扫码快速填写投诉建议。

### 6.2 红线排除（坚决规避）：
*   ~~**SLA 超时提醒与工单状态机 (Ticket Status Workflows)**~~。
*   ~~**多媒体照片/文件上传 (Photo/File Upload)**~~。
*   ~~**客服专员指派与排班系统 (Agent Scheduling & Assignment)**~~。

## 7. 最终决策与红线划分 (Final Decision & Redlines)

### 最终决策：**Merge into existing Topic `contact-us` with Template-only coverage (合并入现有的 `contact-us` 专题，仅做模板库覆盖)**

*   **核心依据**：
    1.  **产品功能存在体验卡点**：服务请求与投诉场景对“文件上传（截图）”和“工单流转”的需求是刚性的。我们 MVP 现阶段无法提供。
    2.  **避免过度承诺**：如果将 `service-request` 或 `customer-complaint` 独立立项为解决方案页，会面临极大的功能缺口质问。
    3.  **合并套利**：我们建议将此词包合并到已有的 `Contact Inquiry` (联系我们/官网咨询) 主题下。在模板库中增加简易的 `customer-complaint-form` (客户意见反馈表) 和 `service-request-form` (服务申请表) 两个模板以承接长尾自然流量，但在营销层面不单独建立 Solution 或 Use Case 页面。
    4.  **警告提示**：在模板描述中，明确说明这是一个**“快速意见收集表（Intake only）”**，不提供照片上传和工单状态管理，建议配合 SlackWebhooks 做通知。
